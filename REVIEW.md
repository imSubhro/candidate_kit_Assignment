# REVIEW.md – Starter `app/main.py` Defect Analysis

Reviewer: Subhro Mohanta  
Kit version reviewed: initial commit (starter `app/main.py`, 5 467 bytes)

---

## Defects found

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|-------|---------------|---------------------|----------------|
| 1 | `health()` | Always returns 200 even when MongoDB is unreachable. No ping is attempted. | Start the app with `MONGO_URI` pointing to a non-existent host; `GET /health` still returns `{"status":"ok"}` instead of 503. | Wrapped in `try/except`: call `db.command("ping")`; if it throws, return 503. |
| 2 | `MongoClient` (module level) | Created at import time, not in `lifespan`. If env vars are set after the module is loaded they are ignored. No `tz_aware=True`, so PyMongo returns naive datetimes; `.astimezone(IST)` on a naive datetime silently uses the host's local zone, not UTC, corrupting IST conversions. | `MongoClient(..., tz_aware=True)` missing; any timezone subtraction (`punch_in - shift_start`) is undefined behavior on Windows and wrong on non-UTC Linux boxes. | Moved client creation into `lifespan`; added `tz_aware=True` and `serverSelectionTimeoutMS=2000`. |
| 3 | `load_dotenv()` | Called with default `override=True` semantics (dotenv default). Real environment variables (e.g., those injected by the grader's Docker) would be silently overridden by a stale `.env`. | Run with `MONGO_URI` set in the shell environment but a different value in `.env`; the `.env` value wins. Spec says real vars must win. | Changed to `load_dotenv(override=False)`. |
| 4 | No indexes | `db.employees` and `db.attendance_logs` have no indexes created. No `lifespan` hook. | Every query is a COLLSCAN. At 100k records, list endpoints become seconds-slow. The unique `{emp_code, date}` index (the concurrency guarantee for punch-in) is absent entirely. | Added `lifespan` with idempotent `create_index` calls for all 8 indexes specified in the contract. |
| 5 | `create_employee` – check-then-insert race | Uses `find_one` before `insert_one`. Two concurrent identical `emp_code` requests both pass the check and one 500s with an unhandled `DuplicateKeyError` (or both insert if the index is missing). | Send 20 parallel `POST /employees` with the same `emp_code`; observe mix of 201 and 500. | Removed the `find_one` check entirely. Relied solely on the unique index; catch `DuplicateKeyError` → 409. |
| 6 | `create_employee` – `created_at` naive | `datetime.now()` is naive (no tzinfo). Stored as local time instead of UTC; varies per deployment timezone. | On a non-UTC server the stored time is wrong. PyMongo with `tz_aware=True` will also reject naive datetimes on reads back (microsecond issues). | Changed to `datetime.now(tz=UTC)`. |
| 7 | `list_employees` – wrong skip formula | `skip = page * page_size` instead of `(page - 1) * page_size`. Page 1 skips the first 20 records; page 0 would return the first page (but page 0 is supposed to be 422). | `GET /employees?page=1&page_size=20` returns records 21-40 instead of 1-20. | Changed to `(page - 1) * page_size`. |
| 8 | `list_employees` – wrong `total` | `count_documents({})` counts the whole collection regardless of the `department` filter applied. | `GET /employees?department=Engineering` with 3 engineers and 10 total employees returns `total: 10` instead of `total: 3`. | Changed to `count_documents(filt)` where `filt` is the same filter object. |
| 9 | `list_employees` – no `page_size` cap / no `page` validation | `page_size` is an unconstrained `int`; `page=0` is silently accepted. | `GET /employees?page_size=10000` returns all docs in one shot; `page=0` skips 0 docs and returns the first page instead of 422. | Added `Query(ge=1)` for page and `Query(ge=1, le=100)` for page_size at all list endpoints. |
| 10 | `list_employees` – no sort | No `.sort()` applied; order is insertion order (undefined after updates). | Records come back in different order across different MongoDB deployments; grader expects `emp_code` asc. | Added `.sort("emp_code", ASCENDING)`. |
| 11 | `punch_in` – epoch seconds vs milliseconds | `datetime.fromtimestamp(body.punched_at / 1000)` divides a user-supplied integer by 1000 but never validates it. A value that looks like seconds (e.g., `1720000000`, 10 digits) would be treated as `1720000` ms = year 1970, not 422. Float values, strings, and booleans are also accepted silently. | Send `"punched_at": 1720000000` (10 digits, looks like seconds); get a 1970 record. Send `"punched_at": 1.5e12`; observe float accepted. | Replaced `Optional[int]` with `Optional[StrictInt]` + custom validator enforcing `[100000000000, 4102444800000]`. |
| 12 | `punch_in` – naive datetime stored | `datetime.fromtimestamp(ms / 1000)` (no `tz=UTC`) creates a local-time naive datetime. Stored in MongoDB as local time, not UTC. IST conversion then uses the wrong base. | On a UTC+0 machine results appear correct; on any other timezone the punch_in time is wrong. | Changed to `ms_to_dt(ms)` which uses `datetime.fromtimestamp(ms // 1000, tz=UTC)`. |
| 13 | `punch_in` – no R1 overnight logic | `ts.date().isoformat()` computes the attendance date from the raw IST date without the overnight-shift correction. An overnight employee punching in at 02:00 (which belongs to the previous shift day) gets today's date. | EMP0005 (shift 22:00-06:00) punches in at 2026-07-07 02:00 IST; date is stored as 2026-07-07 instead of 2026-07-06. | Replaced with `compute_attendance_date()` implementing full R1 overnight logic. |
| 14 | `punch_in` – check-then-insert race | `find_one` check before `insert_one`, same as employees. No concurrency guarantee. | 20 parallel punch-ins produce multiple 201s or a 500. | Removed the `find_one` check; rely on the unique `{emp_code, date}` index catching `DuplicateKeyError` → 409. |
| 15 | `compute_late_minutes` – wrong IST context & wrong comparison | Computes `start = punch_in.replace(hour=h, minute=m, ...)`. If `punch_in` is a naive local datetime this `replace` is on the wrong date. Also `minutes > 10` is wrong — grace is "strictly more than 10:00" (600 s), meaning `>=10 min 0 s + 1 s → late_minutes = 10`. The code uses `> 10` minutes (i.e., > 600 s = 601 s is late=10, correct), but measures from `start` not `shift_start`, and there's no floor — `int((dt - start).total_seconds() / 60)` is integer division which is floor for positive values, but `int()` truncates toward zero, so negative values (before shift_start) would return negative minutes. | `punch_in 09:40:01` with shift 09:30: diff = 601 s → `minutes = int(601/60) = 10`, `10 > 10` is False → returns 0. But correct answer is 10 minutes (late). The condition should be `diff_seconds > 600`, not `minutes > 10`. | Rewrote as `compute_late_minutes` using `diff_seconds = int((pin_ist - shift_start_dt).total_seconds())`: if `diff_seconds <= 600` → 0 else `diff_seconds // 60`. |
| 16 | `compute_work_hours` – banker's rounding | `round(hours, 2)` uses Python banker's rounding. `16182 s = 4.495 h` rounds to 4.49 (bankers) instead of 4.50 (half-up), giving wrong `half_day`. | `punch_in 09:30, punch_out 14:03:02 (16182 s)` → `work_hours = 4.49`, `half_day = true`, but spec says 4.50, `half_day = false`. | Replaced with `Decimal` half-up: `round_half_up(Decimal(secs) / Decimal(3600), 2)`. |
| 17 | `compute_overtime` – wrong IST datetime construction & missing 30-min threshold | `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` on a naive date produces wrong results when shift_end is overnight (next day). Also `max(0, int(...))` returns any positive value, but spec says overtime is 0 unless >= 30 min. | Shift 09:30-18:30, punch_out 18:45 (15 min over) → returns 15 instead of 0. Overnight shift_end comparison is also off. | Rewrote `compute_overtime_minutes_with_overnight`: `diff_seconds < 1800 → 0` else `diff_seconds // 60`. |
| 18 | `list_attendance` – loads entire collection into memory | `list(db.attendance_logs.find(q))` then `docs.sort(...)` in Python. With 100k records this loads all matching documents into memory before paginating. | At 100k records, any unfiltered request OOMs or is seconds-slow. | Changed to `.find(filt).sort([...]).skip(skip).limit(page_size)` with `count_documents(filt)` separately. |
| 19 | `list_attendance` – wrong `total` | `total = len(docs)` counts the in-memory filtered (but un-paginated) slice — after pagination. It counts only the current page size worth, not the true total. Wait — actually it counts all docs matching the filter but that's loaded into memory (`list(find(q))`). At 100k this is memory-expensive and still wrong if a filter produces > one page. Actually the bug is both: loads all into memory AND the total is pre-pagination length but also exposes OOM risk. | `GET /attendance?emp_code=EMP0001` with 200 records: total = 200 (correct coincidentally), but the real bug is the memory load. With no filter: loads 100k docs, then total is 100k, but the memory usage is extreme. | Replaced with `count_documents(filt)` for total and cursor-based pagination. |
| 20 | `list_attendance` – `_id` leaks as string | `d["id"] = str(d.pop("_id"))` renames `_id` to `id` and includes it in the response. The spec says `_id` must never appear in responses. | Response body contains `"id": "..."` field. | Removed entirely; `_id` excluded via `{"_id": 0}` projection or stripped in `serialize_attendance`. |
| 21 | `punch_in` – `doc["id"]` leak | Same issue: `doc["id"] = str(res.inserted_id)` adds a spurious `id` field to the response. | Response contains `"id": "ObjectId(...)"`. | Removed. |
| 22 | No validation on many fields | `EmployeeIn` has no regex validators for `emp_code` (`^EMP\d{4,6}$`), no email format check, no shift time format check, no joined_on calendar validation (`2026-02-30` accepted), no `shift_start == shift_end` guard. `PunchInIn.status` accepts any string including `ABSENT`. | `POST /employees` with `emp_code: "X"` returns 201 instead of 422. | Added `@field_validator` for every field per the contract, plus `@model_validator` for shift equality. |
| 23 | All endpoints as `async def` with sync PyMongo | All route functions are `async def` with synchronous PyMongo calls inside. Sync I/O inside an async function blocks the event loop; the grader sends parallel requests. | Under load, all requests queue behind each other despite the async signature. | Changed all route functions to plain `def` (FastAPI runs them in a threadpool). |

## Things inspected and judged NOT defects

| Item | Judgement |
|------|-----------|
| Using PyMongo (sync) instead of Motor | Acceptable per spec ("PyMongo (sync) or Motor"); plain `def` endpoints make it thread-safe. |
| No `requirements.txt` changes in starter | The starter's `requirements.txt` already included `fastapi`, `uvicorn`, `pymongo`, `pydantic`, `python-dotenv`. I added nothing except what I actually import (`bson` is part of `pymongo`). |
| No `.env` in repo | Correct; `.env.example` is provided for local convenience. |
| Sample data `_id` fields absent | Correct; `mongoimport` / `sample_seed.py` generates them. |
